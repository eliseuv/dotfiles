1. System overview

The dashboard runs on wheatley, the always-on server. Every remote operation, read or write, leaves wheatley as an SSH login to a dedicated remote-control user on the target host. That user's only key is pinned to a forced command that accepts a fixed set of verbs, and polkit grants it exactly the privileges those verbs need. One unprivileged daemon behind nginx, svcctl, does the work through two APIs: /api/svc/ issues commands and serves live status and the tile list, and /api/hosts/ (its host_pages.py module) is a read-only API over host generations and deploy state.

2. Capabilities fixed at eval time

Nothing in svcctl is configurable at runtime. A host tile names one machine, dashboard.host, and its buttons, terminal, host page and uptime follow from what that machine enables (dashboard/_machines.nix): a host in hosts/ is read from its own my.services through hostSpecs, the shared layer of its config that lib/default.nix evaluates once per host for about two seconds in all; the NAS, outside the flake, is read from homelab.externalHosts. Service tiles still set unit (and unitHost). The tiles themselves are declared in wheatley's config (hosts/wheatley/system.nix). At evaluation the modules under modules/nixos/homelab/dashboard/ turn those declarations into one JSON config for svcctl in the Nix store, plus polkit rules, nginx locations and the Homepage config. svcctl receives the config's path as argv, so a request can only name a tile; it can never name a unit, host or command. The config's tiles list is the public part: what each tile shows and which buttons it has, in dashboard order, served at /api/svc/tiles to the dashboard, the rofi menu and the bar alike. Unit names, SSH targets and MACs stay in the private sections. hosts.nix contributes the pages section through an internal option.

Each target entry carries a hosts list: [] for wheatley itself, otherwise the MagicDNS name followed by the mDNS name (or an external machine's address). The target hosts generate their side of the contract from the same my.services.* flags the dashboard reads, so the two can no longer disagree; each host also asserts those flags are set in its default.nix, the only file the dashboard reads them from (homelab/dashboard-reads.nix).

3. Command path: a remote switch

Every write follows the same pattern: an authenticated POST names an action and a tile, svcctl looks the tile up in its eval-time JSON, and runs either a local systemctl call or one SSH verb on the target. Long-running actions return 202 immediately; a watcher thread then polls the target, and the page re-reads /api/svc/status on a back-off schedule. The sequence below shows "switch GLaDOS to latest master".

Other actions are shortcuts of the same path:

  • Wake: no SSH. svcctl broadcasts a magic packet to 255.255.255.255:9; the ping thread later reports up.
  • Power off: one SSH verb to the tile's host (mDNS or address), with no MagicDNS fallback.
  • Reboot, Tailscale on/off, remote unit start/stop/restart: host_action(), the same remote_any() fallback as switch. Local targets use systemctl --no-block under svcctl's polkit rules.
  • Switch log: a GET, so it is unauthenticated. It runs switch-log over SSH (journalctl, last 300 lines, capped at 256 KiB).

4. Read path: host pages and status

Two independent read mechanisms exist. svcctl keeps live state in memory, maintained by background threads, and serves it from /api/svc/status without touching the network on the request path. Its host_pages.py module keeps deploy state: generations, closure diffs and whether each host runs what master evaluates to, cached on disk so a powered-off host still shows its last report.

5. Target side: the forced command

modules/nixos/services/remote-control.nix is the contract every remote host signs. It is enabled when any of remotePowerOff, dotfilesSwitch, remoteTailscale or a non-empty remoteUnits is set.

  • One key, one command. authorized_keys holds restrict,command="<dispatch>" <svcctl@wheatley>: no PTY, no forwarding, and the client's command reaches the script only as $SSH_ORIGINAL_COMMAND.
  • Verbs exist only if enabled. The dispatcher is a case generated per host; disabled features have no arm, and the fallthrough logs refused and exits 1. Numeric arguments (diff N, compare A B) are validated by regex or by host-report itself.
  • No sudo. polkit rules keyed on subject.user == "remote-control" allow exactly the logind actions and manage-units verbs the dispatcher uses. Tailscale goes through two root oneshot units, because the CLI only obeys its operator.
  • No logind session. A PAM rule jumps over pam_systemd for this user. Without it, the polling logins (then one per poll, now one per connection) spun up and tore down user@.service, and a switch landing mid-teardown failed.
  • Switch runs as a unit, not in the SSH session. dotfiles-switch.service builds as the primary user and activates as root through systemd's + prefix. It pulls anonymously over HTTPS and only tries to push the generation tag.

6. Enforcement layers

From the outside in, each layer restricts what the next one can be asked to do. The eval-time allowlist and polkit are each enforced twice: once on wheatley and once on the target.

8. Findings

Resolved: a "read-only" daemon holding the command key. hostctl ran separately but held a second copy of svcctl's key, which the targets' forced command could not tell apart, so its read-only property existed only in its own code. It is now a module of svcctl, so there is one process and one key copy, and nothing claims a boundary that doesn't exist. A real boundary would still be possible: a second, read-only key pinned to a dispatcher that accepts only the report and *-status verbs, used by the host pages.
Resolved: switch logs readable without the login. /api/svc/switch-log/ returned up to 300 journal lines of build and activation output to anyone on the LAN or tailnet. It now needs the login, like the actions; the host page offers it on a 401.
Resolved: the action password crossing the LAN in cleartext. Everything behind the login now answers only from the tailnet's addresses (and this host). From the LAN, nginx refuses with 403 in its rewrite phase, before auth_basic could send a 401 that prompts a browser for the password; the rofi menu won't send it when it reached Wheatley over the LAN. Reads stay open on the LAN. Left as is: a browser that logged in over the LAN before this change may resend those cached credentials until it restarts.
Concurrent switch starts. The ExecCondition mutual exclusion between the two switch units can be raced by two simultaneous starts. This is acknowledged and mitigated by the UI disabling both buttons; acceptable for a single-operator homelab.
